# Decisions

Short records of settled choices, so nobody (human or agent) re-opens them by accident.
Add new ones at the bottom with a date. To change one, add a new entry that says which one it
replaces.

| # | Decision | Why |
|---|---|---|
| D1 | **Spec-driven, agent-built.** `AGENTS.md` holds the rules; `docs/` holds spec, architecture, contracts, plan. Agents build numbered steps from `docs/plan.md` with a coder → tester → reviewer loop (`/build-steps`). | Agents write most of the code; one shared source of truth keeps them consistent. |
| D2 | **Small numbered steps, every step tested.** The full check (pytest, Vitest, lint, build) must pass before a step is done. The human commits a batch of steps as one commit; agents never commit. | Later steps must not silently break earlier ones; humans stay in control of history. |
| D3 | **Simple over fast.** No performance work, concurrency or extra frameworks until all MVP features work. | Course project; readable code for 4 teammates matters more. |
| D4 | **Stack:** FastAPI + SQLModel/SQLite backend; React + TS + Vite + Tailwind + Zustand frontend. shadcn/ui optional. | Standard, light, good for streaming; SQLite is a local file with nothing to install. |
| D5 | **The v0 UI is the visual base** (vertical Plan/Map/Book tabs, draggable divider, history rail, "Why this?", stepper, "+" picker, light theme). | Already built and agreed by the team (`docs/preview/`). |
| D6 | **Free services only, no credit card:** TAMU AI (LLM), Open-Meteo (weather + city geocoding), Geoapify (places/geocoding) with Nominatim fallback, Leaflet + OSM tiles (map), SerpApi free plan (hotel prices). No Google Maps Platform. | Google requires billing; we want zero cost. |
| D7 | **LLM: TAMU AI via an OpenAI-compatible adapter first;** `fake` provider for offline dev and tests. Provider SDKs only in `app/llm/`. Other adapters (e.g. Anthropic) later if needed. | Free for us; adapter keeps it swappable. |
| D8 | *(Replaced by D24.)* **No LLM tool-calling.** Each turn = one JSON "understand" call (profile updates + action) and then either a streamed reply or the generation pipeline (code calls tools → one JSON compose call → postprocess). | Works with any model, easy to test, no fragile tool loops. |
| D9 | **A letter tag on every stop** (home, airports, hotel, places), assigned by code, stable across versions, retired letters never reused. No H1/H2. | Matches the v0; one simple rule for users. |
| D10 | **Facts come from code/tools, never from LLM text:** tags, coordinates, weather, hotel prices, links. LLM-only costs are labeled "AI estimate". | Grounded, honest plan. |
| D11 | **Editing via chat; each edit = a new full version.** Changed items are marked with `updated_in_version` and highlighted. | Simple to build; the highlight shows what changed. |
| D12 | **Flights are link-only in the MVP** (Google Flights deep link, "check link"). Real fares are a stretch step. | No free flight API worth the effort right now. |
| D13 | **No stored provider transcripts;** context is rebuilt each turn from messages + profile + compact itinerary. | Provider-neutral, simpler DB. |
| D14 | **No separate frontend mock mode;** run the backend with `LLM_PROVIDER=fake` + `TOOL_PROVIDER_MODE=mock`. `?demo=1` loads the fixture trip for screenshots. | One code path for the UI. |
| D15 | **MVP audience & scope:** ages 15–35, adults, 2–4 day trips (max 7), 1–2 cities, budget by default, one hotel per city, °F / miles. | Covers the common case. |
| D16 | **TAMU AI settings (verified 2026-11-06, step 10):** base URL `https://chat-api.tamu.ai/openai`, model `protected.Claude-Opus-5`, key starts with `sk-`. Streaming is truly incremental. JSON mode (`response_format: json_object`) and strict `json_schema` both work. **The adapter must send `stream=False` explicitly for non-streamed calls:** if `stream` is left out, the server streams anyway, and the `openai` SDK returns a raw string. Stream chunks can have empty `content` (two interleaved chunk ids), so skip empty deltas. | Found by a throwaway SDK check; step 12 builds on it. |
| D17 | **`budget_level` stays `null` in the profile until the user states it** (2026-11-07, step 16). "Default budget" is applied when a plan is generated and listed as an assumption ("Budget level assumed (none given)"). The understand call never fills defaults; a failed understand call falls back to a plain chat turn with no profile changes. | Contracts: unknown values are `null`, never placeholders; the San Jose fixture profile has `budget_level: null`. |
| D18 | **`complete_json` uses `response_format: json_object` with the schema in the system text, not `json_schema`** (2026-11-07, replaces that part of D16). The adapter takes the first JSON object in the reply (code fences or extra text are ignored), validates it with Pydantic, and retries once. | TAMU AI routes through LiteLLM to Bedrock, whose schema mode rejects `maxItems`/`minimum`/`maximum` and then answers "Schema is too complex" for `TurnAnalysis`. D16's check only used a tiny schema. Bigger schemas (steps 18–22) would fail the same way. |
| D19 | **The Generate button runs the same turn as chat, minus the user message and the understand call** (2026-11-07, step 23). Both paths emit `status → itinerary`, then stream a short LLM summary that is saved as an assistant message with `itinerary_version`. A failed compose saves nothing (previous plan stays) and ends with `error`. | One code path for "make the plan"; every plan version gets a chat message, so the chat can show "Plan updated · vN". |
| D20 | **A Regenerate button re-runs Generate once a plan exists** (2026-11-07, user request after step 24; built in step 26). Same `POST /sessions/{id}/generate` call, so no contract change; it saves the next version, and §3 keeps letters for stops that stay. Targeted changes still go through chat edits (step 25). | Users asked for a one-click "try again" when the first plan isn't to their liking; reusing the generate path keeps it to a frontend change. |
| D21 | **The chat version marker goes after the message that brought the plan** (2026-11-07, step 26; the v0/preview drew it above). The header badge shows the version's `created_at` ("v2 · updated Nov 1, 6:08 PM") instead of a fixed "updated just now". Only Generate/Regenerate swaps an existing plan for skeletons; a chat edit keeps the plan on screen and shows progress as chat status lines. | The marker closes the summary that describes the new version; a real timestamp never goes stale; small edits shouldn't blank the plan. |
| D22 | **No chat-header stepper** (2026-11-07, user request after step 27; reverses part of D5). The "Profile — Trip details — Plan" pills are removed; the profile chips in the Plan header still show what's known and what's missing. | It repeated what the profile chips already show and cluttered the chat header. |
| D23 | **Weather is gathered from the profile, before compose** (2026-11-07, step 30). The pipeline fetches weather for each profile city when exact dates are known (start + end, or start + length); a profile with only rough timing gets no weather. Status lines (`Checking weather for … · Mar 5–7`) appear only during plan generation; a chat turn with no plan yet fetches the forecast for its context silently (no `status` events). A weather `status` with `state: "error"` doesn't fail the generation: the plan is saved with `weather: null` and an assumption. | Matches architecture §4.1 (gather → compose); keeps chat turns free of status lines, so the UI can treat every `status` as plan generation. |

| D24 | **A conversation agent plus a planner agent with LLM tool-calling** (2026-11-08, replaces D8). The conversation agent (understand + chat reply + post-plan summary) works as before. For a generate/edit, a **planner agent** chooses its own tool calls (`search_places`, `search_hotels`, later `search_flights`) over at most **3 rounds of at most 6 calls**. Code runs each round's calls in parallel and feeds the results back, and the planner stops when it asks for no more tools (an edit may ask for none). Then the existing compose call writes the `ItineraryDraft` from every gathered result, cited by ref (`p1`, `h1`…), and postprocess copies the facts (D10 unchanged). Weather stays code-driven (D23). No sub-agents for now; add one per domain later only if its raw results get too big or messy for the planner. **Checked live on TAMU AI (2026-11-08):** OpenAI-format `tools` work on Opus-5 and Sonnet-5. One reply asked for 5 calls at once (weather, 3× places, hotels): round 1 took 5.7 s on Opus and 4.1 s on Sonnet, and the round after results went back took about 2.2 s. `response_format: json_object` also works alongside `tools`. | The team's vision is an agent that decides what to look up. Parallel calls keep it fast: the wait is the number of rounds, not the number of tools. Keeping compose and postprocess keeps the plan grounded and the existing tests valid. |
| D25 | **Concurrency is allowed for tool calls only** (2026-11-08, amends D3): the calls inside one planner round, and weather across cities, run at the same time with `asyncio.gather` + `asyncio.to_thread`. Everything else stays sequential. The 6-call cap keeps Geoapify under its 5 requests/second; `places.py` keeps Nominatim at ≤ 1 request/second with a lock. | A planning wait made of several serial API calls is the slowest part users see; this is the one place concurrency clearly pays. |
| D26 | **One model per role** (2026-11-08). `LLM_MODEL` (`protected.Claude-Opus-5`) runs the planner and compose. `LLM_CHAT_MODEL` (`protected.Claude-Sonnet-5`) runs understand, chat replies and the post-plan summary; it falls back to `LLM_MODEL` when empty. Both go through the same OpenAI-compatible adapter. | Measured on TAMU AI: first streamed token 1.2 s on Sonnet-5 vs 5.3 s on Opus-5. Chat should feel instant; planning benefits from the stronger model. |
| D27 | **Where a stop's coordinates come from** (2026-11-08, step 34; widened in step 34a). In order: the found place its `place_ref` cites; else the same-named stop of an earlier version (edits copy stops with tag keys and no ref); else the places geocoder: home → the profile's origin; airports and the hotel (hotel changed by D30) → the draft's address, or "name, day city" without one; every other stop → "name, day city". For every stop but home the lookup is precise: a city-level geocoder match (Geoapify `result_type` or Nominatim `addresstype`/`type` of city, town, village, county, state, country or postcode) counts as not found, so a stop is pinned only where a real, specific match exists, never at the city centre; home and the city lookups in `search_places` keep city matches. A stop the geocoder doesn't find stays off the map. Never from draft numbers or the weather's city coordinates. Item `source` is "Geoapify" for stops from the places search. Mock mode's geocoder knows only cities, so a precise mock lookup finds only an address (house number first). | The precise check stops wrong city-centre pins, so a name lookup is now safe as the last resort for a stop the model didn't cite (e.g. a new stop in an edit). Addresses geocode better than "name + city" for the fixed points (e.g. IAH isn't in the trip city); an LLM address for an ordinary stop may be made up, so those use the name. Nominatim's 1 request/second makes the fallback slow when many stops lack refs, which is rare with the planner's searches. Hotels get refs in step 37. |
| D28 | **Travel estimate mode** (2026-11-08, step 35). A leg is estimated only between consecutive items of one day at two different stops that both have coordinates (otherwise `null`). Mode: ≤ 1 mile → walk; else the profile's transport (car → drive, transit → transit, rideshare or mixed → rideshare; none → rideshare). The leg right after a flight item is `mode: "flight"` with its distance and `duration_min: null`. Duration = haversine miles ÷ speed (walk 3, transit 12, drive/rideshare 25 mph), rounded to whole minutes (at least 1); distance rounded to 0.1 mi. | Simple, offline, and matches the v0 fixtures (short legs walked, longer ones by rideshare). A routing API would add a key and latency for little gain on a 2–4 day plan; driving speed would make a flight leg absurd. |
| D29 | **SerpApi quota guard** (2026-11-08, step 38). Hotel searches are cached 6 h by (city, check_in, check_out) only, and `registry.PlanLimits` allows one `search_hotels` per city per plan (city = the part before the first comma, case-insensitive); an extra call gets "skipped: limit". Results are cheapest first, keeping ratings ≥ 3.5 (all if none qualify), at most 5. No key, or HTTP 429 / "run out of searches" → lodging places from the places tool with no prices (`price_source: "none"`); other errors → `ok: false`. The cache key and `registry.search_hotels` ignore `adults`, so prices are always for 1 adult (accepted for the MVP). | The free plan is ~250 searches/month, so code, not only the prompt, must stop repeat searches. The cheapest results are often badly rated (1.8 in the step 37 check). |
| D30 | **Hotel prices in the plan** (2026-11-08, step 39). A hotel stop cites a hotels result by ref (`h1`…) and takes its coordinates; "lodging" is no longer a fixed kind, so a hotel without a ref is geocoded by "name, city". Lodging `price_per_night` and `price_as_of` come from the tool; `total_price` = per night × nights (SerpApi's total is for the searched dates, which can differ per city). An edit that keeps the hotel (same name) keeps its tool price from the earlier version. The item source shows the time in UTC. | Prices must never come from the LLM; per-night × nights stays right for split stays. |
| D31 | **Bookings by code, ids from tags** (2026-11-08, step 42). `build_bookings` makes one round-trip flight (`bk-flight`), one per hotel (`bk-hotel-{tag}`) and one per booking-required activity stop (`bk-activity-{tag}`); status carries over by id, and PATCH edits the latest version in place. The "Google Hotels" lodging link is always a Google Hotels search; SerpApi's `link` (the hotel's own website) is a separate "Hotel site" link. | Tags are stable across versions, so ids are too; honest link labels. |
